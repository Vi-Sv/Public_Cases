## Шаг №3. Генерация сырого массива транзакций (1000 строк)
В файле 1_generate_raw_data.ipynb реализован следующий код генерации данных:

```python
# импортируем в сессию библиотеки pandas и numpy, присваивая короткое имя для быстрого вызова
import pandas as pd
import numpy as np
# заходим в библиотеку numpy через короткий алиас np
# далее, через точку-шлюз, обращаемся к внутреннему подмодулю random, относящемуся к библиотеке np, который содержит функции генерации случайных чисел
# через вторую точку-шлюз, обращаемся к методу seed(), который является одной из функций подмодуля random
# метод seed() делает генерацию чисел предсказуемой - является "закладкой в книге", задает фиксированную стартовую позицию, и выдает одну и ту же последовательность (отсылает на один и тот же текст книги)
np.random.seed(42)
# объявляем числовую переменную-константу n_rows, в которую записываем значение 1000
# это наш "архитектурный план" — заданный масштаб, определяющий, сколько строк данных мы создадим во всей последующей цепочке кода
n_rows = 1000
# создаем три изолированных списка (list) в квадратных скобках
# clean_prices — "чистые" цены (положительные целые числа)
# refunds — возвраты/убытки (отрицательные числа, имитирующие финансовый отток)
# garbage — "мусорные" данные для стресс-теста (пустота None, строка-ошибка 'null_error' и строка с пробелами '    ')
clean_prices = [1500, 2500, 5000, 12300]
refunds = [-3000, -4500]
garbage = [None, 'null_error', '    ']
# формируем генеральный массив данных amount_pool ("общий бассейн", откуда мы будем черпать значения)
amount_pool = clean_prices * 4 + refunds * 1 + garbage * 1
# знак умножения (*) для списков в Python не умножает числа
# Знак * для списков в Python работает как копировальный аппарат. Он берет элементы внутри квадратных скобок и повторяет их друг за другом указанное количество раз
# знак плюса (+) склеивает эти размноженные списки в один длинный поезд данных
# clean_prices * 4 берет список из 4 элементов и превращает его в один длинный список из 16 элементов:[1500, 2500, 5000, 12300, 1500, 2500, 5000, 12300, 1500, 2500, 5000, 12300, 1500, 2500, 5000, 12300]
# refunds * 1 оставляет список как есть (всего 2 элемента):[-3000, -4500]
# garbage * 1 тоже оставляет список без изменений (3 элемента):[None, 'null_error', '    ']
# В результате переменная amount_pool становится одним большим списком, в котором лежат 21 элемент
# создаем структуру данных "словарь" (dictionary) через фигурные скобки и записываем её в переменную data
# словарь устроен по принципу "ключ: значение", где каждый ключ (например, 'tx_id') станет будущим названием колонки, а значение — её содержимым
data = {
    # КЛЮЧ 'tx_id' (ID транзакции): через встроенную функцию range() генерируем последовательность целых чисел
    # Функция range() в Python — это встроенный генератор (конвейер) арифметических прогрессий. Она выдает неизменяемую последовательность целых чисел.
    # Функция может принимать от одного до трех параметров: range(start, stop, step).
    # стартуем с 10001 и идем до (10001 + n_rows), то есть до 11001. Верхняя граница в range не включается, поэтому мы получим ровно 1000 уникальных ID по порядку
    # Pandas автоматически «прокрутит» этот конвейер от начала до конца, забирает все 1000 сгенерированных чисел и раскладывает их по строкам сверху вниз.
    'tx_id': range(10001, 10001 + n_rows),
    
    # КЛЮЧ 'user_id' (ID пользователя): ныряем через "точки-шлюзы" np -> random -> к функции randint()
    # randint(501, 550) генерирует случайные целые числа в диапазоне от 501 до 549 включительно (верхняя граница 550 исключается, отсюда ровно 50 уникальных ID клиентов)
    # через параметр size=n_rows приказываем функции выдать не одно число, а сразу заполнить массив длиной в 1000 элементов
    'user_id': np.random.randint(501, 550, size=n_rows), 
    
    # КЛЮЧ 'amount' (сумма): через "точки-шлюзы" np -> random вызываем функцию choice()
    # функция choice() работает как "лотерейный барабан": она принимает наш ранее созданный "бассейн" (amount_pool) и случайно вытаскивает из него элементы
    # параметр size=n_rows заставляет барабан прокрутиться ровно 1000 раз, чтобы на выходе получилась тысяча сумм с учетом заложенных нами перекосов и "мусора"
    'amount': np.random.choice(amount_pool, size=n_rows),
    
    # КЛЮЧ 'tx_date' (дата транзакции): снова используем "лотерейный барабан" choice() для выбора дат из предложенного списка строк
    # список намеренно "грязный": в нем смешаны разные форматы ISO ('2026-08-01'), европейский ('02.08.2026'), с косой чертой ('2026/08/03') и сломанный текст ('broken_date')
    # параметр size=n_rows раскидает эти текстовые даты по всем 1000 строкам будущей таблицы
    'tx_date': np.random.choice(
        ['2026-08-01', '02.08.2026', '2026/08/03', 'broken_date', '2026-08-05'],
        size=n_rows
    )
}
# обращаемся к библиотеке pandas через алиас pd, заходим через "точку-шлюз" в класс-конструктор DataFrame()
# передаем на вход наш структурированный словарь data. Pandas берет ключи и превращает их в шапку таблицы (столбцы), а массивы значений превращает в упорядоченные строки
# результат этой сборки упаковывается в переменную df_raw (сокращение от Dataframe Raw — сырая, необработанная таблица)
df_raw = pd.DataFrame(data)

# вызываем встроенную базовую функцию Python print() для вывода информации на экран
# передаем ей строковое значение (текст в кавычках), которое послужит визуальным разделителем и заголовком в консоли для последующих отчетов
print("--- ТЕХНИЧЕСКИЙ АУДИТ МАТРИЦЫ В RAM ---")
print(f"Формат матрицы (строки, колонки): {df_raw.shape}")
print("\nТипы колонок, определенные Pandas автоматически:")
print(df_raw.dtypes)
print("\nПервые 5 строк грязного сырья:")
print(df_raw.head(5))
```

# синтаксис: таблица (созданная при помощи DataFrame), точка (шлюз доступа к внутреннему инструменту), инструмент перевода (один из) to_csv

## Шаг №9. Создание физического контейнера-приемника (DDL-разметка)

   1. В активном окне SQL-редактора вводится DDL-скрипт для создания таблицы-приемника, состоящей из 4 полей:

* SQL-код (DDL) для создания таблицы.

```sql
-- Стираем старый контейнер, если он остался от прошлых тестов
DROP TABLE IF EXISTS raw_transactions;

-- Формируем новые текстовые секторы на жестком диске под входящие данные
CREATE TABLE raw_transactions (
tx_id VARCHAR(50),
user_id VARCHAR(50),
amount VARCHAR(100),
tx_date VARCHAR(100)
);
```
## Комментарии к DDL-скрипту

   1. DROP TABLE IF EXISTS raw_transactions; — Команда полного удаления файла таблицы raw_transactions с жесткого диска (директория \data), если она была создана ранее.
   2. IF EXISTS — Предохранитель от ошибок при первом запуске скрипта. Если таблица отсутствует, сервер игнорирует команду и переходит к следующей строке.
   3. CREATE TABLE raw_transactions (...); — Выделение нового пустого сектора на жестком диске и регистрация имени таблицы в системном каталоге базы данных case_fintech.
   4. Типы данных полей (Стратегия ELT):
   * tx_id VARCHAR(50) — Текстовое поле переменной длины для идентификатора транзакции (до 50 символов).
      * user_id VARCHAR(50) — Текстовое поле для идентификатора пользователя (до 50 символов).
      * amount VARCHAR(100) / tx_date VARCHAR(100) — Намеренное использование текстового типа вместо NUMERIC или DATE. Это исключает аппаратный отказ СУБД при импорте строк с мусорными значениями (null_error, пробелы). База принимает данные в исходном «грязном» виде для последующей очистки SQL-запросами.
   
Данный скрипт работает на уровне дисковой подсистемы и не задействует оперативную память (RAM).

## Регулярное выражение для валидации целых чисел: ~ '^-?[0-9]+$'
Шаблон фильтрует текстовые поля от нечисловых артефактов перед выполнением арифметических операций и приведением типов в ELT-контуре.
## Разбор синтаксиса регулярного выражения по символам:

* ~ — оператор сопоставления строки с регулярным выражением в СУБД PostgreSQL.
* ^ — якорь начала строки (проверка стартует с первого символа).
* -? — необязательный знак дефиса (минус может встречаться 0 или 1 раз, что позволяет валидировать как положительные, так и отрицательные значения).
* [0-9]+ — диапазон допустимых символов (цифры от 0 до 9), где квантификатор + требует наличия как минимум одного цифрового знака (отсекает пустые ячейки и пробелы).
* $ — якорь конца строки (гарантирует отсутствие посторонних символов, букв или единиц измерения вроде "1500р" после цифрового блока).

Для валидации дробных чисел применяется модифицированная маска: ~ '^-?[0-9]+\.?[0-9]*$'

## Шаг №13. Создание очищенной витрины данных (CREATE VIEW)
Для фиксации логики трансформации на диске проверенный очистной запрос оборачивается в конструкцию VIEW. На базе этого представления формируется финальная агрегация (группировка) для расчета валового оборота по каждому клиенту согласно техническому заданию.

   1. Создание представления (VIEW):

```sql
create or replace view v_clean_transaction as 

SELECT 
tx_id, -- выводим ID транзакции
user_id, -- выводим ID клиента
CASE -- открываем конструкию CASE 
	WHEN amount ~ '^-?[0-9]+$' THEN ABS(amount::NUMERIC)
	ELSE 0 
END AS clean_amount 
	
FROM raw_transactions;
```



   1. Активация скрипта: Запрос выполняется комбинацией клавиш Ctrl + Enter. Созданное представление регистрируется в системном каталоге СУБД.

   1. Финальный расчет валового оборота под требования ТЗ:

Через обращение к витрине v_clean_transactions выполняется группировка (GROUP BY) по полю user_id и расчет суммы очищенных транзакций (SUM(clean_amount)).
Для контроля целостности данных применяется оконная функция над агрегатом COUNT. Это позволяет рассчитать общую сумму всех схлопнутых строк по всей таблице (OVER () с пустыми скобками) и вывести ее сквозным образом в отдельном столбце. Данный маневр гарантирует проверку того, что итоговая сумма строк по всем клиентам строго равна исходным 1000 строкам и при агрегации не произошло потери данных.
Итоговый результат ранжируется по убыванию суммы оборота (ORDER BY ... DESC).

```sql
SELECT -- шаг 3 - выводим необходимые графы, формируя новые имена, соответствующие логике граф
    user_id, -- выводим ID пользователей
    SUM(clean_amount) AS total_turnover, -- суммируем значения из графы clean_amount внутри групп, присваяивая имя
    COUNT(tx_id) AS total_transactions, -- считаем количество ID транзакций (строк) внутри каждой группы, присваивая имя
    
    -- "Контроль целостности данных": считаем сумму всех COUNT по всему окну таблицы
    SUM(COUNT(tx_id)) OVER() AS grand_total_rows 

FROM v_clean_transaction -- шаг 1 - обращаемся к таблице
GROUP BY user_id -- шаг 2 - группируем одноименные значения в графе ID пользователей
ORDER BY total_turnover DESC; -- шаг 4 - сортируем по убыванию
```

## Такт 6. Слой визуализации и сдача отчета (BI)
На данном этапе развитие архитектуры возможно по двум альтернативным сценариям:

   1. «Зависимый источник данных» — передача на дашборд финального агрегированного результата запроса. Требует создания дополнительного представления (VIEW) на базе второго SQL-скрипта.
   2. «Единый источник данных» — передача в BI-систему только очищенного плоского массива данных. Все метрики, группировки, условия и вычисления реализуются непосредственно на стороне BI-платформы.

Приоритетный выбор: Второй вариант является предпочтительным, так как обеспечивает гибкость, универсальность и интерактивность аналитики без жесткой привязки к логике конкретного SQL-запроса. Это позволяет конечным пользователям работать с чистым массивом данных и самостоятельно формировать новые срезы.

При выборе архитектурного пути необходимо учитывать следующие технологические особенности:

## Правила проектирования BI-слоя

* Закон распределения вычислений: Оптимизация производительности BI-системы требует раздельной передачи таблиц (факты, справочники, измерения) с последующим выстраиванием связей внутри BI, вместо импорта одной денормализованной таблицы.
* Закон динамических мер: Вычисления внутри BI-платформ должны реализовываться через динамические меры (агрегирующие функции). Расчеты на уровне вычисляемых столбцов создают избыточную нагрузку на процессор и оперативную память.
* Закон гранулярности: Передача данных должна осуществляться с контролируемым уровнем детализации (например, секционирование по периодам), исключая избыточную загрузку всего исторического массива.

## Реализация сценария в рамках кейса
Для демонстрации вариативности и ввиду малого объема данных выбран гибридный метод: выгрузка данных в промежуточный физический файл CSV с последующим импортом в BI-систему (в реальных высоконагруженных контурах применяется прямое подключение BI к СУБД).
Архитектурный маршрут реализуется по принципу «Единый источник данных». На уровень BI передается плоский массив из первичного SQL-представления (v_clean_transactions), не подвергнутый предварительной агрегации и группировке на стороне СУБД.

## Заключение по Кейсу №1: Завершение сквозного цикла End-to-End
Сквозной цикл обработки данных полностью выполнен по всей цепочке: от исходного файла до финального отчета. Реализована схема передачи и трансформации информации через стек технологий: Python ➔ СУБД PostgreSQL ➔ Выгрузка в CSV ➔ BI-система Yandex DataLens.
## Результаты настройки этапов конвейера:

* Импорт данных: Исходный массив транзакций загружен на локальный сервер PostgreSQL.
* Очистка данных: В СУБД создано представление (VIEW), которое с помощью регулярных выражений автоматически удаляет текстовые ошибки в столбцах и приводит числовые значения к правильному формату.
* Визуализация: В Yandex DataLens настроен итоговый дашборд. Математические операции и группировка перенесены на сторону BI-системы. Сумма валового оборота рассчитывается динамически и составляет 4 340 200 рублей.
* Контроль целостности: Настроенная мера подсчета строк (COUNT) выводит на дашборде ровно 1 000 операций, что подтверждает отсутствие потерь или дублирования информации при экспорте.
