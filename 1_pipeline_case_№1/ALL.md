Шаг 3. Генерация сырого массива транзакций (1000 строк).
1. В открытом окне VS Code, в развернутом контуре файла 1_generate_raw_data.ipynb, прописываем код генерации данных (все необходимые комментарий по написанию кода располагаются внутри самого кода):
# импортируем в сессию библиотеки pandas и numpy, присваивая короткое имя для быстрого вызова
import pandas as pd
import numpy as np
# заходим в библиотеку numpy через короткий алиас np
# далее, через точку-шлюз, обращаемся к внутреннему подмодулю random, относящемуся к библиотеке np, который содержит функции генерации случайных чисел
# через вторую точку-шлюз, обращаемся к методу seed(), который является одной из функций подмодуля random
# метод seed() делает генерацию чисел предсказуемой - является "закладкой в книге", задает фиксированную стартовую позицию, и выдает одну и ту же последовательность (отсылает на один и тот же текст книги)
np.random.seed(42)
# объявляем числовую переменную-константу n_rows, в которую записываем значение 1000
# это наш "архитектурный план" — заданный масштаб, определяющий, сколько строк данных мы создадим во всей последующей цепочке кода
n_rows = 1000
# создаем три изолированных списка (list) в квадратных скобках
# clean_prices — "чистые" цены (положительные целые числа)
# refunds — возвраты/убытки (отрицательные числа, имитирующие финансовый отток)
# garbage — "мусорные" данные для стресс-теста (пустота None, строка-ошибка 'null_error' и строка с пробелами '    ')
clean_prices = [1500, 2500, 5000, 12300]
refunds = [-3000, -4500]
garbage = [None, 'null_error', '    ']
# формируем генеральный массив данных amount_pool ("общий бассейн", откуда мы будем черпать значения)
amount_pool = clean_prices * 4 + refunds * 1 + garbage * 1
# знак умножения (*) для списков в Python не умножает числа
# Знак * для списков в Python работает как копировальный аппарат. Он берет элементы внутри квадратных скобок и повторяет их друг за другом указанное количество раз
# знак плюса (+) склеивает эти размноженные списки в один длинный поезд данных
# clean_prices * 4 берет список из 4 элементов и превращает его в один длинный список из 16 элементов:[1500, 2500, 5000, 12300, 1500, 2500, 5000, 12300, 1500, 2500, 5000, 12300, 1500, 2500, 5000, 12300]
# refunds * 1 оставляет список как есть (всего 2 элемента):[-3000, -4500]
# garbage * 1 тоже оставляет список без изменений (3 элемента):[None, 'null_error', '    ']
# В результате переменная amount_pool становится одним большим списком, в котором лежат 21 элемент
# создаем структуру данных "словарь" (dictionary) через фигурные скобки и записываем её в переменную data
# словарь устроен по принципу "ключ: значение", где каждый ключ (например, 'tx_id') станет будущим названием колонки, а значение — её содержимым
data = {
    # КЛЮЧ 'tx_id' (ID транзакции): через встроенную функцию range() генерируем последовательность целых чисел
    # Функция range() в Python — это встроенный генератор (конвейер) арифметических прогрессий. Она выдает неизменяемую последовательность целых чисел.
    # Функция может принимать от одного до трех параметров: range(start, stop, step).
    # стартуем с 10001 и идем до (10001 + n_rows), то есть до 11001. Верхняя граница в range не включается, поэтому мы получим ровно 1000 уникальных ID по порядку
    # Pandas автоматически «прокрутит» этот конвейер от начала до конца, забирает все 1000 сгенерированных чисел и раскладывает их по строкам сверху вниз.
    'tx_id': range(10001, 10001 + n_rows),
    
    # КЛЮЧ 'user_id' (ID пользователя): ныряем через "точки-шлюзы" np -> random -> к функции randint()
    # randint(501, 550) генерирует случайные целые числа в диапазоне от 501 до 549 включительно (верхняя граница 550 исключается, отсюда ровно 50 уникальных ID клиентов)
    # через параметр size=n_rows приказываем функции выдать не одно число, а сразу заполнить массив длиной в 1000 элементов
    'user_id': np.random.randint(501, 550, size=n_rows), 
    
    # КЛЮЧ 'amount' (сумма): через "точки-шлюзы" np -> random вызываем функцию choice()
    # функция choice() работает как "лотерейный барабан": она принимает наш ранее созданный "бассейн" (amount_pool) и случайно вытаскивает из него элементы
    # параметр size=n_rows заставляет барабан прокрутиться ровно 1000 раз, чтобы на выходе получилась тысяча сумм с учетом заложенных нами перекосов и "мусора"
    'amount': np.random.choice(amount_pool, size=n_rows),
    
    # КЛЮЧ 'tx_date' (дата транзакции): снова используем "лотерейный барабан" choice() для выбора дат из предложенного списка строк
    # список намеренно "грязный": в нем смешаны разные форматы ISO ('2026-08-01'), европейский ('02.08.2026'), с косой чертой ('2026/08/03') и сломанный текст ('broken_date')
    # параметр size=n_rows раскидает эти текстовые даты по всем 1000 строкам будущей таблицы
    'tx_date': np.random.choice(
        ['2026-08-01', '02.08.2026', '2026/08/03', 'broken_date', '2026-08-05'],
        size=n_rows
    )
}
# обращаемся к библиотеке pandas через алиас pd, заходим через "точку-шлюз" в класс-конструктор DataFrame()
# передаем на вход наш структурированный словарь data. Pandas берет ключи и превращает их в шапку таблицы (столбцы), а массивы значений превращает в упорядоченные строки
# результат этой сборки упаковывается в переменную df_raw (сокращение от Dataframe Raw — сырая, необработанная таблица)
df_raw = pd.DataFrame(data)

# вызываем встроенную базовую функцию Python print() для вывода информации на экран
# передаем ей строковое значение (текст в кавычках), которое послужит визуальным разделителем и заголовком в консоли для последующих отчетов
print("--- ТЕХНИЧЕСКИЙ АУДИТ МАТРИЦЫ В RAM ---")
print(f"Формат матрицы (строки, колонки): {df_raw.shape}")
print("\nТипы колонок, определенные Pandas автоматически:")
print(df_raw.dtypes)
print("\nПервые 5 строк грязного сырья:")
print(df_raw.head(5))

Шаг №8. Создание физического контейнера-приемника (DDL разметка)
1. В центре интерфейса отображается окно скрипта для ввода кода, сюда и вводим код по созданию таблицы – контейнера, которая будет состоять из 4 граф:
-- Стираем старый контейнер, если он остался от прошлых тестов
DROP TABLE IF EXISTS raw_transactions;

-- Формируем новые текстовые секторы на жестком диске под входящие данные
CREATE TABLE raw_transactions (
tx_id VARCHAR(50),
user_id VARCHAR(50),
amount VARCHAR(100),
tx_date VARCHAR(100)
);

Комментарий к коду:
1) DROP TABLE IF EXISTS raw_transactions – Это приказ серверу PostgreSQL пойти на жесткий диск в папку \data и полностью физически стереть файл таблицы raw_transactions со всеми строками, если он там лежал от прошлых запусков.
2) IF EXISTS (Если существует) – Это предохранитель на случай самого первого запуска скрипта. Если бы мы запустили этот скрипт в самый первый раз, а таблицы на диске еще не было, мы столкнулись бы с ошибкой: «Таблица raw_transactions не найдена». Предохранитель IF EXISTS приказывает серверу: «Если таблицы нет — просто пропусти эту строчку и иди дальше».
3) CREATE TABLE raw_transactions ( ... ); – Данная команда формирует на жестком диске новый пустой сектор, регистрируя имя табдицы в системном каталоге базы данных case_fintech. В круглых скобках задаем разметку внутренних ячеек.
4) Внутри скобок мы перечисляем имена будущих вертикальных столбцов и задаем их тип:
tx_id VARCHAR(50)
•	Создаем колонку для ID транзакций. Тип VARCHAR(50) означает: «Переменное количество текстовых символов (Variable Character), но не более 50 штук в одной ячейке».
user_id VARCHAR(50)
•	Создаем колонку для ID пользователей. Тоже резервируем под нее текст до 50 символов.
•	amount VARCHAR(100)
•	tx_date VARCHAR(100)
Ключевой маневр контура А (ELT): Для суммы (amount - остаток) и даты (tx_date) мы намеренно выбрали текстовый тип VARCHAR(100) вместо логичных цифровых типов NUMERIC или DATE. 
Если бы мы указали тип NUMERIC, а в нашем грязном CSV-файле на диске лежит строка со значением "null_error" или " " - (просто пробел), то при импорте, жесткий диск сервера PostgreSQL выдал бы аппаратный отказ.
Заявив тип VARCHAR, мы говорим серверу: «Принимай в эти ячейки абсолютно любой текстовый мусор». 
База без проблем примет грязный CSV-файл на диск, а хирургическую чистку мы сделаем позже с помощью SQL-запросов.
Для понимания, данный код не касается оперативной памяти, он работает исключительно на женском диске, создавая физический контейнер для приема данных.

2. Пишем SQL запрос, согласно нашей цели, а именно: 
– пустоты NULL и текстовый мусора (null_error, пробелы) нужно ликвидировать — заменим их на числовой 0 [инструмент COALESCE].
– Ошибка возвратов (отрицательные числа) нужно развернуть в абсолютную величину [инструмент ABS].
– Весь этот текстовый винегрет VARCHAR нужно принудительно перевести в строгий математический тип данных для проведения математических расчетов [инструмент CAST или оператор ::NUMERIC].

Продвинутый маневр – чтобы перевести грязную графу, содержащую и числа и текстовый шум в числовой формат, применим следующую конструкцию «ЕСЛИ ТО»:
CASE 
 -- Если в текстовой ячейке лежит строго число (с минусом или без), безопасно плавим в формат numeric и берем модуль ABS, избавляясь от минуса
     WHEN amount ~ '^-?[0-9]+$' THEN ABS(amount::NUMERIC)
-- Любой буквенный мусор, пробелы или NULL принудительно переводим в безопасный ноль
     ELSE 0
END AS clean_amount 

Сила маски: ~ '^-?[0-9]+$'
Данная маска является универсальным решением для целых чисел: сито для очистки текстовых полей от грязи перед математическими операциями. Для аналитика в ELT-контуре это главный щит.
Разбирем физику этой маски по символам:
•	~ — это оператор PostgreSQL, который означает: «Проверь строку на соответствие текстовому шаблону (маске)».
•	^ — маркер начала строки. Процессор проверяет строку с самого первого символа.
•	-? — знак минуса и вопрос после него. Вопрос означает: «Минус может быть один раз, а может вообще отсутствовать» (так мы ловим и положительные числа, и отрицательные возвраты).
•	[0-9]+ — квадратные скобки задают диапазон (любая цифра от 0 до 9), а плюс означает «цифр должно быть одна или больше». Это отсекает пустые строки и пробелы.
•	$ — маркер конца строки. Означает, что после цифр в строке не должно быть вообще ничего. Любая буква в конце (как "1500р") сломает проверку.
Для дробных чисел маска будет чуть сложнее: ~ ^-?[0-9]+\.?[0-9]*$

Шаг №12. Создание очищенной витрины данных (CREATE VIEW).
Наша задача — обернуть проверенный очистной запрос в конструкцию VIEW и сразу провести финальную агрегацию (группировку), чтобы посчитать честный валовой оборот по каждому клиенту, как требовало ТЗ.
1. Для начала формируем «линзу» – VIEW.
create or replace view v_clean_transaction as 

SELECT 
tx_id, -- выводим ID транзакции
user_id, -- выводим ID клиента
CASE -- открываем конструкию CASE 
	WHEN amount ~ '^-?[0-9]+$' THEN ABS(amount::NUMERIC)
	ELSE 0 
END AS clean_amount 
	
FROM raw_transactions;

2. Активируем код комбинацией ctrl + Enter и наблюдаем в дереве навигации созданное «Представление», рисунок 26.
Рисунок 26 – Результат выполнения кода по созданию «Представления» (витрины)
 
Физически таблица v_clean_transactions не располагается нигде на жестком диске. У неё нет физического размера в мегабайтах, и она не занимает место на складе базы данных. Представление v_clean_transactions — это виртуальный фильтр, та самая «линза», через которую мы смотрим на основной, грязный массив данных, наблюдая только необходимое.



3. Далее, формируем SQL запрос под ТЗ:
Обращаясь к созданному представлению, мы говорим: «Зайди в таблицу v_clean_transaction (блок FROM), сгруппируй» все одноименные строки в графе user_id (блок GROUP BY), в каждой группе собери сумму значений по графе clean_amount (агрегатор SUM).
- Важный маневр: «контроль целостности данных», для этого нам необходимо посчитать количество ID самих транзакций – строк. Так как в запросе мы применяем группировку, таблица физически схлопывается, если при этом мы посчитаем количество строк через COUNT, напротив каждой строки мы получим внутреннее количество строк, которые схлопнул GROUP BY, чтобы осуществить контроль над количеством и убедиться, что запрос не потерял строки (что явно исказило бы истинность результата), мы применим оконные функции, а именно: сформируем графу, где сумму количества (сумму значений из графы COUNT) приклеим к абсолютно каждой строчке, взяв за «виртуальную группу» абсолютно всю таблицу (то есть в OVER () мы оставляем пустые скобки, показав тем самым, что за группу мы и берем всю таблицу).
В конце причесываем запрос сортировкой по убыванию через ORDER BY _ DESC.
SELECT -- шаг 3 - выводим необходимые графы, формируя новые имена, соответствующие логике граф
    user_id, -- выводим ID пользователей
    SUM(clean_amount) AS total_turnover, -- суммируем значения из графы clean_amount внутри групп, присваяивая имя
    COUNT(tx_id) AS total_transactions, -- считаем количество ID транзакций (строк) внутри каждой группы, присваивая имя
    
    -- "Контроль целостности данных": считаем сумму всех COUNT по всему окну таблицы
    SUM(COUNT(tx_id)) OVER() AS grand_total_rows 

FROM v_clean_transaction -- шаг 1 - обращаемся к таблице
GROUP BY user_id -- шаг 2 - группируем одноименные значения в графе ID пользователей
ORDER BY total_turnover DESC; -- шаг 4 - сортируем по убыванию

Такт 6. Слой визуализации и сдача отчета (BI)
Мы находимся в точке, где движение дальше возможно по двум вариантам:
1. «Зависимый источник данных»: Мы передаем на дашборд последний результат запроса, который уже отображает необходимы результат под ТЗ. Для этого из второго запроса мы должны сформировать еще одно представление «VIEW».
2. «Единый источник данных»: Мы передаем на дашборд только очищенные данные, а все необходимые условия, метрики, группы и математику выполняем внутри BI-системы.
При этом, второй вариант является предпочтительным, из-за своей потенциальной гибкости, универсальности и интерактивности, и не зависит от тех условий, которые мы сформировали вручную в SQL-запросе. Это позволяет каждому просматривать исходные, но уже очищенные данные, а также проводить необходимые манипуляции для получения новых результатов. Но и он не лишен минусов, при выборе одного их двух путей следует понимать:
1. Закон распределения вычислений: Bi-система также зависима от производительности, не стоит кидать на дашборд одну большую и сложную таблицу, состоящую из нескольких (факты, справочники, измерения) – лучшим выбором будет отдать таблицы в Bi-систему отдельно и наладить связи внутри.
2. Закон динамических мер: любая математика в Bi только через меры (агрегирующие функции). Меры считаются динамически для определенных данных, в то время как математика между полноценными столбцами вынуждает системы проводить больше операций, которые могут быть вообще не нужны.
3. Закон гранулярности: логическая передача данных, к примеру: по периодам, а не весь массив очищенных данных.
В рамках данного кейса реализуем сценарий с выгрузкой данных в физический файл (формат CSV) и его последующую передачу в BI-систему, выбор такого сценария аргументирован небольшим объемом данных и демонстрации вариативности (в последующем будем передавать данные напрямую через подключение Bi – системы к базе данных). После передачи экспортированных данных, развернем финальную аналитическую трансформацию под поставленную задачу.
Маршрут из точки осуществим по первому варианту - «Единый источник данных». На уровень BI передадим результат выполнения первичного SQL-представления, еще не подвергнутого агрегации и группировке.
